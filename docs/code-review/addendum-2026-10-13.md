## New findings (all fixed in this pass)

### F-50 · Compare page crashes when a pillar list is absent

**Severity:** High · **Category:** Correctness · **Status:** Fixed

**Where:** `components/analyzer/compare/listed-compare.tsx:93-94`, `components/analyzer/compare/unlisted-compare.tsx:38-39`

**What:** `va?.pillars.find(...)` only guards `va` being null/undefined; if `verdict` exists but `pillars` itself
is `undefined` (an older or degraded summary, or a run where pillar scoring didn't complete), `.find` is called
on `undefined` and throws. The line just above already handles the same case correctly with `va?.pillars ?? []`,
so the missing `?.` here was an oversight, not a design choice.

**Fix:** Added the missing optional-chain: `va?.pillars?.find(...)` / `vb?.pillars?.find(...)` in both files.

### F-51 · Sizing-tier rows in compare pair two companies' tiers by array position

**Severity:** Medium · **Category:** Correctness · **Status:** Fixed

**Where:** `components/analyzer/compare/listed-compare.tsx:105-110`, `components/analyzer/compare/unlisted-compare.tsx:49`

**What:** The "B" column of each sizing-tier row was `sizeB[i]`/`sb[i]`, matched purely by array index to
`sizeA[i]`/`sa[i]`. The two tier lists come from two independent analysis runs with no guarantee of matching
order or length, so a run whose tiers come back in a different order (or with a tier missing) would show one
company's numbers under the other company's tier label.

**Fix:** Match tiers by `portfolio_name` (`sizeB.find((x) => x.portfolio_name === t.portfolio_name)`) instead of
by index, in both files.

### F-52 · Charts can index past the bar array after an interval switch

**Severity:** High · **Category:** Correctness · **Status:** Fixed

**Where:** `components/orderflow/flow-chart.tsx:39-44,80`, `components/technicals/indicator-chart.tsx:113-132`

**What:** Hover position is kept in local `useState` as a raw index and is never re-validated against the
current bar count; `idx = hover ?? n - 1` clamps a `null` hover but not a stale one. Hovering near the end of a
longer series (e.g. order flow's `1m`, ~390 bars) and then switching to a shorter interval (e.g. `1d`, ~60 bars)
via a control outside the chart's `onMouseMove` area leaves `hover` pointing past the new, shorter `data.bars`.
The next render does `data.bars[idx]` → `undefined`, and the very next line (`bar.c >= bar.o`) throws
`TypeError: Cannot read properties of undefined`, crashing the chart (there is no error boundary — see F-11).

**Fix:** Changed the clamp to `idx = hover != null && hover < n ? hover : n - 1` in both files, so a hover index
from a longer series falls back to the last bar of the new, shorter one instead of being used as-is.

### F-53 · RSI reads "overbought" for a stock that hasn't moved at all

**Severity:** Medium · **Category:** Integrity · **Status:** Fixed

**Where:** `backend/app/services/indicators.py:32-39` (`rsi`)

**What:** When price is flat for a full window (gain == 0 and loss == 0 — a halted or limit-locked symbol, or a
thinly traded stock with an unchanged close for ≥14 bars), `rs` is `0/NaN = NaN`, but the override condition
`(loss == 0) & gain.notna()` was true (gain is `0.0`, not `NaN`), forcing the result to `100` — "extremely
overbought" for a stock that hasn't traded away from its last price. `mfi()` just below guards the identical
degenerate case with an extra `pos > 0` check and deliberately leaves it undefined; `rsi()` lacked that guard.
This surfaced in `technicals.py` as a plausible-looking but wrong `"Overbought"` signal.

**Fix:** Added the same `gain > 0` condition RSI's sibling `mfi()` already uses, so a genuinely flat window
returns `NaN` (rendered as "no signal") instead of being forced to 100.

### F-54 · VWAP doesn't guard NaN volume, unlike the other volume-weighted indicators

**Severity:** Low · **Category:** Robustness · **Status:** Fixed

**Where:** `backend/app/services/indicators.py:139-153` (`vwap`)

**What:** `vwap_bands()` and `relative_volume()` both call `df["Volume"].fillna(0.0)` before using it; `vwap()`
used `df["Volume"]` directly. `clean_frame()` in `technicals.py` only drops rows with a NaN Close/High/Low, so a
bar with a NaN Volume but valid OHLC can reach `vwap()` and poison that bar's cumulative sum with `NaN` (bounded
to that bar under pandas' default `skipna=True` cumsum, not every later bar).

**Fix:** `vwap()` now fills NaN volume with `0.0` before use, matching its siblings.

### F-55 · `ApiRisk`'s ATR-derived fields are typed non-nullable but can be `null`

**Severity:** Medium · **Category:** Correctness · **Status:** Fixed

**Where:** `backend/app/services/risk_layer.py:57,72,96-97`; `lib/api/types.ts` (`ApiRisk.metrics.atrPct`,
`ApiRisk.sizing.stopPrice`, `ApiRisk.sizing.stopPct`); `components/technicals/risk-card.tsx:67-74`

**What:** `atr_pct = atr_v / last * 100 if last else float("nan")` treats a last close of exactly `0.0` (bad or
sparse vendor data, a halted stock, a corporate-action glitch) the same as a missing value and produces `NaN`,
which `_f()` serializes as `null`. `stop_pct` (`2 * atr_pct`) and `stopPrice` inherit the same `null`. The
TypeScript types declared all three as plain `number` (unlike the already-correctly-nullable
`maxPositionPct`), and `RiskCard` interpolated them directly (`{m.atrPct}%`), which would have rendered the
literal string `"null%"` for that symbol rather than crashing — still a wrong, user-visible display.

**Fix:** Typed `atrPct`, `stopPrice` and `stopPct` as `number | null` in `lib/api/types.ts`, and updated
`RiskCard` to render `—` for each when null, matching the existing treatment of `maxPositionPct`.

### F-56 · GEX only loads half the intended option-expiry depth

**Severity:** Medium · **Category:** Correctness · **Status:** Fixed

**Where:** `backend/app/services/options_gex.py:66-86` (`_load_chain`), `MAX_EXPIRIES = 6` at line 29

**What:** The loop appends two rows to `frames` per expiry (one for calls, one for puts) but broke on
`len(frames) >= MAX_EXPIRIES`. After 3 expiries, `len(frames) == 6 == MAX_EXPIRIES`, so the loop stopped before
a 4th expiry was ever fetched — half the documented 6-expiry depth. This is not a crash: it silently understates
`totals.gexMillions`/`dexMillions`/`thetaPerDay`/`vegaPerPoint` and can misplace the gamma flip and OI walls,
for any symbol with more than 3 listed expiries inside 45 days (true most trading days for SPY/QQQ, which have
weekly and monthly expiries).

**Fix:** Changed the break condition to count expiries actually processed (`len(skipped) >= MAX_EXPIRIES`)
rather than the row count in `frames`.

## Findings not carried forward

Two lower-confidence candidates were raised during this pass and are noted here rather than given an F-number,
per the review's own bar (a nameable trigger, not a theoretical gap):

- `options_gex.py` totals/`zeroDte` fields are built with `_f()` and could in principle serialize as `null`,
  but every sum in the current code runs over rows already filtered to `oi > 0` and finite IV, so no concrete
  triggering input was found.
- `CompareMenu`'s initial peers/`runs` effect is gated on `!open || runs`; if the component instance ever
  persisted across a change of `run.id` without remounting, suggestions could go stale. Whether Next.js
  remounts this component on the relevant navigation was not confirmed either way.
